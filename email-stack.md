# A Maildir-First Email Stack for Corporate Mail

This is the shape of the mail setup I use for corporate email. It is built
around a local Maildir, with Outlook 365 on the remote side, `mbsync` as my
IMAP synchronizer, `aerc` as my mail client, `maildir-sieve` for local
rule-based filing, `maildir-pushd` for push synchronization, and `msmtpq` plus
`msmtp` for outgoing mail.

The examples below are real in structure, but sanitized. Addresses, list names,
tenant details, and mailbox names are fake.

The motivation is not nostalgia for terminal mail clients. I am a developer,
and a large part of my daily email workflow is plain text. I read and write
technical threads, send patch series generated by `git format-patch`, and
review changes that arrive as email. For that kind of work, the email client
has to preserve text faithfully, handle patches without getting in the way, and
make it easy to move between mail, an editor, and the command line.

Outlook's web interface is not built for that workflow. Thunderbird is much
better as a mail client, but it still feels like a general-purpose graphical
client first. `aerc` is closer to the way I actually work: fast keyboard
navigation, local files, good text handling, and easy integration with external
tools. The other practical reason is performance. Outlook 365's IMAP service
can be extremely slow, so I do not want the UI blocked on live IMAP operations
for every mailbox interaction.

So this is intentionally not a "mail client talks directly to IMAP" setup. My
client talks to local files. Synchronization, filtering, OAuth2, queueing, and
address completion are separate pieces that I can inspect and debug
independently.

## What I Wanted

The main things I wanted were:

- keep `aerc` fast by making it read and write a local Maildir;
- keep the remote Outlook 365 mailbox synchronized through IMAP;
- apply filing rules locally instead of doing slow server-side moves;
- avoid a search index or tag database just to decide where messages belong;
- support offline or unreliable-network sending;
- keep authentication compatible with corporate OAuth2 requirements;
- make the system observable through logs.

The important constraint is that this is still corporate mail. The canonical
server is Outlook 365, and I cannot pretend the local Maildir is the only
truth. Local state has to make its way back to IMAP: moved messages, deleted
messages, read flags, and sent mail all have to synchronize eventually.

## The Final Data Flow

The inbound path looks like this:

```text
Outlook 365 IMAP
        |
        | mbsync --pull work
        v
~/.mail/.../new/
        |
        | aerc opens the mailbox and acknowledges messages
        v
~/.mail/.../cur/
        |
        | maildir-pushd notices cur/ changes
        | maildir-sieve files new Inbox messages
        | mbsync --push work publishes local changes
        v
Outlook 365 IMAP
```

The key design rule I ended up with is that only one component consumes Maildir
`new/`: the MUA. In my setup, that is `aerc`.

`mbsync` delivers new local messages into `new/`. `aerc` sees them, displays
them, and moves them into `cur/` as part of normal Maildir handling. Only after
that does automation react. `maildir-pushd` watches `cur/` directories,
debounces the changes, runs local filtering for newly acknowledged Inbox
messages, and then pushes the resulting local state back to IMAP.

That gets filtering off the server without letting a separate filter process
race with the MUA for ownership of `new/`.

## IMAP Synchronization With mbsync

`mbsync` is responsible for moving state between Outlook 365 and the local
Maildir. The sanitized account looks like this:

```ini
IMAPAccount work
Host outlook.office365.com
Port 993
TLSType IMAPS
AuthMechs XOAUTH2
User me@corp.example
PassCmd "python3 ~/.mutt/mutt_oauth2.py ~/.mutt/me@corp.example.tokens"

IMAPStore work-imap
Account work

MaildirStore work-maildir
SubFolders Verbatim
Path ~/.mail/
Inbox ~/.mail/INBOX

Channel work
Far :work-imap:
Near :work-maildir:
Patterns "Archive" "Deleted Items" "Drafts" "INBOX" "INBOX/*" "Junk Email" "Sent Items"
Expunge Both
Create Both
SyncState *
```

The channel is bidirectional, but the commands are deliberately split by
direction:

```sh
mbsync --pull work
mbsync --push work
```

Pulls are caused by explicit checks or IMAP notifications. Pushes are owned by
the local Maildir monitor. That split matters because incoming mail and local
state changes are different events:

- "new mail arrived on the server" means "pull it locally";
- "local Maildir changed" means "push the change back to IMAP".

My old model tried to do too much in one script. The new model lets each event
run the minimum command that makes sense.

## The Pull Script

The script is still called `fetchmail.sh`, although it does not use fetchmail.
At this point the name is historical. Its job is to serialize remote pulls and
write useful logs:

```sh
#!/bin/sh

set -e

if [ "${FETCHMAIL_JOURNAL:-0}" != 1 ] && command -v systemd-cat >/dev/null 2>&1; then
        FETCHMAIL_JOURNAL=1 exec systemd-cat \
                -t fetchmail \
                -p info \
                --stderr-priority=err \
                "$0" "$@"
fi

(
        if ! flock -w 60 9; then
                printf '%s fetchmail: skipped, lock was held for more than 60s\n' "$(date -Is)"
                exit 1
        fi

        printf '%s fetchmail: start\n' "$(date -Is)"
        trap 'status=$?; printf "%s fetchmail: end status=%s\n" "$(date -Is)" "$status"; exit "$status"' EXIT

        printf '%s fetchmail: mbsync pull\n' "$(date -Is)"
        mbsync --pull work

        addr_cache=~/go/bin/maildir-rank-addr
        if [ -x "$addr_cache" ]; then
                printf '%s fetchmail: refresh address cache\n' "$(date -Is)"
                "$addr_cache" || printf '%s fetchmail: address cache refresh failed status=%s\n' "$(date -Is)" "$?"
        fi
) 9> /tmp/fetchmail.lock
```

Both `aerc` and IMAP notification can call this script. The shared lock keeps
those pull triggers from competing with each other, and also prevents a pull
and a push batch from stepping on each other.

Because this is a plain script, its journal entries are not attached to a
dedicated systemd unit. They are tagged instead:

```sh
journalctl --user -b -f \
  SYSLOG_IDENTIFIER=fetchmail \
  + _SYSTEMD_USER_UNIT=maildir-pushd.service \
  + _SYSTEMD_USER_UNIT=goimapnotify@outlook.service
```

## Maildir `new/` and `cur/`

Maildir has three directories per mailbox:

- `tmp/` is for in-progress delivery;
- `new/` is for newly delivered messages that have not been acknowledged by a
  mail reader;
- `cur/` is for messages that a mail reader has seen as part of normal mailbox
  operation.

This is separate from the IMAP `Seen` flag. A message can be in `cur/` and
still be unread. In Maildir filenames, unread messages simply lack the `S` flag
after the `:2,` suffix.

For example:

```text
new/1770000000.12345_1.host
cur/1770000000.12345_1.host:2,
cur/1770000000.12345_1.host:2,S
```

The first message has not been acknowledged by the MUA. The second has been
acknowledged but is unread. The third has been acknowledged and marked seen.

This distinction drove a lot of the final design. Treating "not seen" as "new"
is wrong, because I often leave messages unread for days. Treating files in
`new/` as filter input also creates a race: both the MUA and the filter would
be trying to consume the same Maildir handoff. Watching `cur/` avoids that.

## Local Filtering With maildir-sieve

[`maildir-sieve`](https://github.com/jp39/maildir-sieve) is the local filtering
tool. It evaluates Sieve rules against Maildir messages and applies the filing
decisions locally.

I kept it deliberately small. The useful action subset is:

- `fileinto`;
- `fileinto :copy`;
- `keep`;
- `discard`, only when explicitly allowed;
- `imap4flags` operations such as `addflag "\\Seen"`.

The project uses
[`github.com/foxcpp/go-sieve`](https://github.com/foxcpp/go-sieve) for the
Sieve interpreter and
[`github.com/emersion/go-maildir`](https://github.com/emersion/go-maildir) for
Maildir operations. I preferred relying on `go-sieve` to inventing another
mail filtering language, especially now that recent versions support the
extensions this setup needs. Thanks to Max Mazurov, the `go-sieve` author, for
making that possible.

One limitation compared to Sieve running at delivery time on an IMAP server is
that `maildir-sieve` only sees the message as stored in the Maildir. It can
inspect headers and body, but it does not have access to SMTP or LMTP envelope
information unless that information was preserved in headers by the server. For
my rules this is acceptable, but it is a real difference from server-side Sieve
where tests such as `envelope` can match the original delivery recipient.

A sanitized Sieve script looks like this:

```sieve
require ["fileinto", "copy", "imap4flags"];

if header :contains "from" "ci@example.net" {
  fileinto "INBOX/Builds";
  stop;
}

if header :contains ["to", "cc"] "project-list@corp.example" {
  fileinto "INBOX/Lists/Project";
  stop;
}

if header :contains ["to", "cc"] "reviews@corp.example" {
  if anyof (
    header :contains "from" "me@corp.example",
    header :contains "to" "me@corp.example"
  ) {
    fileinto :copy "INBOX/Reviews/Mine";
  }
  fileinto "INBOX/Reviews";
  stop;
}

if header :contains "to" "announcements@corp.example" {
  addflag "\\Seen";
  fileinto "INBOX/Announcements";
  stop;
}
```

For manual testing:

```sh
maildir-sieve \
  -maildir ~/.mail \
  -source INBOX \
  -script ~/.config/maildir-sieve/filter.sieve \
  -limit 20
```

Apply mode changes the Maildir:

```sh
maildir-sieve \
  -maildir ~/.mail \
  -source INBOX \
  -script ~/.config/maildir-sieve/filter.sieve \
  -apply
```

When `maildir-sieve` moves a message between folders, it strips local
mbsync-style `,U=<number>` markers from the filename. Those markers represent
the IMAP UID for one specific mailbox. Reusing the same UID marker in another
Maildir folder would lie to `mbsync` about which remote message the local file
corresponds to.

## Watching and Pushing With maildir-pushd

[`maildir-pushd`](https://github.com/jp39/maildir-pushd) is the glue that makes
local filtering fit the Maildir model.

It watches every Maildir `cur/` directory below the Maildir root. It ignores
`new/` and `tmp/` for decisions. When a file appears in `INBOX/cur`, it treats
that as "a newly delivered Inbox message has now been acknowledged by the MUA"
and runs `maildir-sieve` on that file. When any meaningful `cur/` change occurs,
it schedules a debounced push:

```sh
maildir-pushd \
  -maildir ~/.mail \
  -source INBOX \
  -script ~/.config/maildir-sieve/filter.sieve \
  -push-cmd 'mbsync --push work' \
  -lock-file /tmp/fetchmail.lock
```

The user service is straightforward:

```ini
[Unit]
Description=Watch Maildir changes and push them to IMAP

[Service]
Type=simple
Environment=PATH=%h/.local/bin:/usr/local/bin:/usr/bin:/bin
ExecStart=%h/.local/bin/maildir-pushd \
        -maildir %h/.mail \
        -source INBOX \
        -script %h/.config/maildir-sieve/filter.sieve \
        -push-cmd "mbsync --push work" \
        -lock-file /tmp/fetchmail.lock
Restart=on-failure
RestartSec=5s

[Install]
WantedBy=default.target
```

The important point is that `maildir-pushd` does not only exist for filtering.
I also want normal MUA changes to make it back to the server. If `aerc` marks a
message read, moves a message, or deletes a message, that is a local Maildir
change that should be pushed back to IMAP. The daemon centralizes that
responsibility instead of making every tool remember to run `mbsync --push`.

## aerc as the Maildir Client

`aerc` is configured as a local Maildir client:

```ini
[Work]
source             = maildir://~/.mail
check-mail-cmd     = fetchmail.sh
check-mail         = 600s
check-mail-timeout = 120s
outgoing           = msmtpq
default            = INBOX
from               = Example User <me@corp.example>
signature-file     = ~/.config/aerc/signature.txt
pgp-auto-sign      = true
address-book-cmd   = grep -i -m 50 --color=never %s ~/.mail/addressbook
```

That means the UI is never waiting on IMAP for normal browsing. It reads local
files and shells out when I explicitly need synchronization or sending.

There was a tempting design where IMAP notification would call into aerc over
IPC and ask it to run `:check-mail`. That would make aerc the visible entry
point for new mail checks. I decided against that. The better boundary is lower
level: notifications trigger the pull script, `aerc` consumes Maildir `new/`,
and `maildir-pushd` reacts after files reach `cur/`.

## IMAP Notifications

`goimapnotify` is used to avoid waiting for the periodic aerc check. It opens an
IMAP IDLE connection to the corporate server and runs the pull script when
interesting mailboxes change:

```json
{
  "host": "outlook.office365.com",
  "port": 993,
  "tls": true,
  "username": "me@corp.example",
  "passwordCmd": "python3 ~/.mutt/mutt_oauth2.py ~/.mutt/me@corp.example.tokens",
  "xoauth2": true,
  "onNewMail": "~/.local/bin/fetchmail.sh",
  "wait": 5,
  "boxes": [
    "INBOX",
    "Sent Items"
  ]
}
```

I also watch `Sent Items` because outgoing messages may appear there through
server-side behavior or another client. The local copy still has to be kept
coherent.

## Outgoing Mail With msmtpq and msmtp

Outgoing mail uses `msmtpq` from `aerc`:

```ini
outgoing = msmtpq
```

`msmtpq` acts like a sendmail-compatible command. It writes a message body and
the corresponding `msmtp` arguments into a queue directory, then tries to send.
If the network is unavailable or SMTP fails, the message stays queued.

The queue lives under:

```text
~/.msmtp.queue/
```

Queue logs live under:

```text
~/log/msmtp.queue.log
```

The management wrapper is `msmtp-queue`:

```sh
msmtp-queue -d   # display queued mail
msmtp-queue -r   # flush the queue
msmtp-queue -R   # send selected queued messages
msmtp-queue -p   # purge selected queued messages
```

I also have cron retry delivery periodically, so a temporary SMTP or network
failure does not require me to remember to flush the queue manually:

```cron
*/30 * * * * bash -lc "msmtp-queue -r"
```

`msmtp` itself talks to Office 365 SMTP with XOAUTH2:

```ini
account office365
    host smtp.office365.com
    port 587
    tls on
    tls_starttls on
    auth xoauth2
    user me@corp.example
    passwordeval python3 ~/.mutt/mutt_oauth2.py ~/.mutt/me@corp.example.tokens
    from me@corp.example

account default : office365
```

The queue gives `aerc` a fast, local handoff for outgoing mail, just as Maildir
gives it a fast, local view for incoming mail.

## OAuth2 and XOAUTH2

I use the same OAuth2 helper for IMAP, SMTP, and IMAP IDLE:

```sh
python3 ~/.mutt/mutt_oauth2.py ~/.mutt/me@corp.example.tokens
```

The helper is `mutt_oauth2.py`, which originally comes from the Mutt ecosystem.
I am not using Mutt as the MUA in this setup, but the script is useful on its
own because it does one job well: keep an encrypted OAuth2 token file and print
a valid access token for other tools.

`mbsync` calls it through `PassCmd`, `msmtp` calls it through `passwordeval`,
and `goimapnotify` calls it through `passwordCmd`.

The helper stores OAuth state in an encrypted token file. The token file
contains bearer tokens, so it is treated as sensitive state:

```text
~/.mutt/me@corp.example.tokens
```

The authorization setup is done once:

```sh
python3 ~/.mutt/mutt_oauth2.py ~/.mutt/me@corp.example.tokens --authorize
```

After that, normal commands just ask the helper for an access token. If the
access token is still valid, it prints it. If it has expired but the refresh
token is still valid, it refreshes the access token, updates the encrypted token
file, and prints the new token.

The corporate Microsoft registration needs scopes equivalent to:

```text
offline_access
https://outlook.office.com/IMAP.AccessAsUser.All
https://outlook.office.com/SMTP.Send
```

`offline_access` is what makes refresh tokens available. Without it, unattended
sync would eventually stop when the short-lived access token expires.

For IMAP, the token is used as an XOAUTH2 secret. For SMTP, `msmtp` also uses
XOAUTH2. No app password is involved.

## Address Completion From Existing Mail

I generate address completion from the local Maildir using
`maildir-rank-addr`:

```toml
maildir = "~/.mail"
outputpath = "~/.mail/addressbook"
template = "{{.Address}}\t{{.Name}}\t{{.NormalizedName}}"
```

That produces a local text file:

```text
~/.mail/addressbook
```

`aerc` then uses a simple lookup command:

```ini
address-book-cmd = grep -i -m 50 --color=never %s ~/.mail/addressbook
```

This is intentionally boring. The address book is not my source of truth for
contacts. It is a ranked cache derived from already received mail. `fetchmail.sh`
refreshes it after a successful pull, so the same refresh happens whether the
pull was triggered by `goimapnotify` or by `aerc`. That works well for corporate
email because the most useful addresses are usually the people and lists that
already appear in the mailbox.

## Design History

I went through several other designs before ending up with the current model.

### Server-side imapfilter

My original setup ran `imapfilter` against the Outlook 365 IMAP server before
syncing locally. That had one big advantage: all filing happened remotely, so
`mbsync` only had to mirror the result.

The downside was latency. Server-side IMAP searches and moves against a large
corporate mailbox were slow, and every new-mail event could trigger a long
remote filtering pass. It also made rule evaluation dependent on server
behavior and network round trips.

Server-side filtering is conceptually clean, but for my mailbox it was too slow
in practice.

### A simple pull, filter, push script

The next idea I tried to reason through was:

```sh
mbsync --pull work
maildir-sieve -maildir ~/.mail -source INBOX -script ~/.config/maildir-sieve/filter.sieve -apply
mbsync --push work
```

This is still a useful batch shape, and it is how I can test `maildir-sieve`
manually. But making it the normal live path has problems:

- every check runs two sync operations, even if there is nothing to push;
- the script wants to process Maildir `new/`, which races with the MUA;
- local MUA changes outside the script still need a separate push;
- IMAP notifications and aerc-initiated checks become hard to coordinate.

The final setup keeps the good part, local filtering, but separates the pull
event from the push event.

### notmuch and afew

`notmuch` and `afew` were attractive because they are mature tools for indexing
and tagging mail. The experiment worked in principle: I could index the
Maildir, use queries to classify messages, and let `afew` apply tags.

The issue was that the desired output was not "this message has tag X". The
desired output was "move this message to folder Y and synchronize that move
back to IMAP".

That made the notmuch database feel like extra machinery for my actual goal:

- initial indexing of a large Maildir takes real time;
- the index has to be maintained;
- tags introduce a second state model in addition to IMAP folders and flags;
- another step is needed to convert tags into Maildir moves;
- if the database gets stale, filing decisions become harder to reason about.

`notmuch` is still excellent for search-heavy workflows. For this problem, it
felt counterproductive. My rules only need message headers and bodies, and the
only durable result I want is a Maildir change.

### mbsync hooks or aerc filtering plugins

Another possible place to solve this was inside an existing program:

- a hook in `mbsync`, so filtering could happen as part of delivery;
- a filtering plugin or hook in `aerc`, so messages could be filed after the
  client acknowledges them.

That would have been attractive because it removes one external daemon. The
problem, for me, is that neither boundary was quite right.

`mbsync` is a synchronizer, not a local delivery agent. Its job is to make the
near side and far side converge while maintaining sync state. A per-message
filter hook in the middle of that operation would have to be very carefully
defined, especially if the hook moves files between Maildir folders while
`mbsync` is still reconciling UIDs and flags.

`aerc` is the MUA, and it is exactly the component that consumes Maildir `new/`.
But making filtering depend on aerc-specific hooks would tie the whole mail
pipeline to one client. That is more invasive than watching the Maildir state
that aerc already produces.

The final model keeps both tools in their natural roles: `mbsync` synchronizes,
`aerc` reads mail, and an external monitor reacts to committed local state.

### Python Sifter

I also looked at Python Sifter as an alternative Sieve implementation. In other
words, it would still let me write Sieve rules; the difference is that the
filtering engine is written in Python rather than Go. The drawback was
extension coverage and fit. I specifically wanted standard-ish Sieve with
`fileinto`, `copy`, and `imap4flags`.

`go-sieve` had moved far enough that it supported the extensions needed here,
and building a small Go command around it made deployment simple: one static-ish
binary and no Python environment dependency for the filtering path.

### Patching aerc

Another possible solution was to make aerc directly aware of the problem:

- block Maildir new-mail processing while `check-mail-cmd` runs;
- add an aerc hook after messages move from `new/` to `cur/`;
- integrate filtering directly into aerc;
- submit the hook upstream.

That would solve the race close to the MUA, but it makes my mail stack depend
on aerc changes. Carrying a local patch is annoying, and getting a new hook
accepted upstream is a separate project.

The current design avoids that dependency. `aerc` remains a normal Maildir MUA.
My automation watches the filesystem boundary that already exists.

### Blocking filesystem events externally

At one point I wondered whether the race could be fixed from the outside by
blocking filesystem event delivery. The scenario was: `mbsync` creates a file
in `INBOX/new/`, `aerc` notices it and moves it to `cur/`, while a separate
filtering process also wants to treat that same file as new mail. If I could
temporarily stop aerc from seeing the event, maybe the filter could run first.

That is not a good abstraction. inotify is a notification mechanism, not a
coordination mechanism. A program can watch changes, debounce them, and respond,
but it cannot reliably make another independent process stop receiving or
acting on filesystem state.

In the end, coordination is done with locks around sync commands and by
choosing a clean ownership boundary: `new/` belongs to the MUA, `cur/` changes
are observable state.

### A shell-only inotify monitor

A small `inotifywait` script could have watched `INBOX/cur` and called the
filter. But that only covers automatic filing of newly acknowledged Inbox
messages. The more important case is ordinary MUA activity: I can move a mail
from one folder to another, mark it read, delete it, or otherwise change local
Maildir state, and those changes still need to be pushed back to IMAP.

That means the monitor soon needed to do more:

- watch every Maildir `cur/` directory, not just Inbox;
- detect folder moves as a remove event in one mailbox and a create event in
  another;
- discover newly created folders;
- debounce bursts of events;
- serialize filtering before pushing;
- share a lock with pull commands;
- handle timeouts and service restarts;
- avoid refiltering renames caused by `mbsync` UID assignment.

At that point, a dedicated Go daemon was simpler and more reliable than a large
shell script.

## Operational Notes

Useful logs are in the user journal:

```sh
journalctl --user -b -f \
  SYSLOG_IDENTIFIER=fetchmail \
  + _SYSTEMD_USER_UNIT=maildir-pushd.service \
  + _SYSTEMD_USER_UNIT=goimapnotify@outlook.service
```

`fetchmail` is a journal tag, not a unit name, because it is a script run by
other programs through `systemd-cat`.

`maildir-pushd` logs its own batches, including when it queues a filter, when
it runs a push, and whether commands fail. `mbsync` may also log harmless
provider-specific warnings. For example, Outlook may not support every local
Maildir flag, so a warning about not propagating an unsupported flag is not
necessarily a sync failure.

One subtle detail is `mbsync`'s local UID markers. Filenames can contain pieces
like:

```text
,U=9159
```

That UID belongs to one IMAP mailbox. When a message is moved to another folder,
the marker has to be removed so `mbsync` can upload or associate the message
correctly in the destination mailbox. Preserving the old marker across folders
can make the synchronizer believe the file corresponds to the wrong remote UID.

## The Result

This is not the smallest possible mail setup, but that is not really what I was
optimizing for. I wanted each component to have a narrow job:

- `mbsync` synchronizes IMAP and Maildir;
- `fetchmail.sh` performs serialized pulls;
- `aerc` reads and writes the local Maildir;
- `maildir-sieve` makes deterministic local filing decisions;
- `maildir-pushd` watches local changes and pushes them back;
- `msmtpq` queues outbound mail;
- `msmtp` sends through Office 365 SMTP;
- the OAuth2 helper supplies XOAUTH2 tokens;
- `maildir-rank-addr` builds a local address-completion cache.

The main lesson, for me, is that Maildir's `new/` and `cur/` split is not
incidental. It is the contract that lets the pieces avoid stepping on each
other. Once `new/` is treated as the MUA handoff and `cur/` is treated as
committed local state, the rest of the design becomes much easier to reason
about.

## Software Used

The main pieces of software in this setup are:

- [aerc](https://aerc-mail.org/) - the terminal mail client I use as my MUA.
- [isync / mbsync](https://isync.sourceforge.io/) - the IMAP-to-Maildir synchronizer.
- [goimapnotify](https://gitlab.com/shackra/goimapnotify) - the IMAP IDLE notifier that triggers pulls when remote mailboxes change.
- [maildir-sieve](https://github.com/jp39/maildir-sieve) - my local Sieve-based Maildir filtering tool.
- [maildir-pushd](https://github.com/jp39/maildir-pushd) - my Maildir monitor that runs filters and debounces `mbsync --push`.
- [maildir-rank-addr](https://github.com/ferdinandyb/maildir-rank-addr) - the address-completion cache generator.
- [msmtp](https://marlam.de/msmtp/) - the SMTP client used for outgoing mail.
- [msmtpq / msmtp-queue](https://marlam.de/msmtp/msmtpq/) - the queue wrapper around `msmtp`.
- [Mutt's `mutt_oauth2.py`](https://gitlab.com/muttmua/mutt/-/blob/master/contrib/mutt_oauth2.py) - the OAuth2 token helper reused by `mbsync`, `goimapnotify`, and `msmtp`.
